# Runbook — What Must Never Be Committed to GitHub

This is the authoritative list of files, values, and artifacts that must never
be pushed to the `irexpro` repository (or any fork/clone of it). The
`.gitignore` excludes most of these automatically; this document exists so
operators and engineers know **why** each is excluded and can spot-check before
pushing.

---

## 1. Files that must never be committed

| Path / pattern | Why | `.gitignore` entry |
|---|---|---|
| `apps/api/.env` | Contains real DB/authentication/provider/payment credentials and encryption material | `.env` + `.env.*` (with `!.env.example` exception) |
| `services/ai-engine/.env` | Contains real Redis password, internal API key | `.env` + `.env.*` (with `!.env.example` exception) |
| `apps/api/dist/` | Build output — regenerated on every build; tracking it causes merge noise and ships stale code | `dist/` |
| `**/node_modules/` | Dependencies — installed via `pnpm install`, not committed | `node_modules/` |
| `services/ai-engine/.venv/` | Python virtualenv — installed via `pip install` | `.venv/` + `venv/` |
| `**/__pycache__/` | Python bytecode cache | `__pycache__/` + `*.pyc` |
| `coverage/` | Test coverage output | `coverage/` |
| `.next/`, `.turbo/`, `.cache/`, `build/` | Build caches | individual entries |
| `*.log`, `logs/` | Application logs (may contain request data, internal IDs) | `*.log` + `logs/` |
| `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.crt`, `*.csr` | TLS/signing keys and certificates | individual entries |
| `id_rsa*`, `id_ed25519*` | SSH private keys | individual entries |
| `*.egg-info/` | Python package metadata (auto-generated by `pip install -e .`) | see §6 |
| `.DS_Store`, `Thumbs.db` | OS artifacts | individual entries |
| `.vscode/`, `.idea/` | Editor configs (may contain local paths/secrets) | individual entries |

### 2.1 What placeholders ARE acceptable in committed files

Only non-real, obviously fake placeholders are acceptable in `.env.example`,
docs, and tests, for example:

- `CHANGE_ME_*`
- `PLACEHOLDER`
- `dev_internal_key_change_me`
- deterministic test-only strings that cannot authenticate to a real provider

Do not paste copied production/staging values into examples even temporarily.

## 3. Pre-push self-check

Before every `git push`, run the repository's tracked-source secret scan and
review staged files. At minimum verify:

```bash
# Confirm no real .env files are staged
git diff --cached --name-only | grep -E '\.env$' && echo "BLOCK: .env staged" || echo "OK: no .env staged"

# Confirm no build/runtime artifacts are staged
git diff --cached --name-only | grep -E '(^|/)(dist|node_modules|\.venv)/' && echo "BLOCK: build artifact staged" || echo "OK: no build artifacts"

# Inspect staged changes for common provider/token prefixes
git diff --cached | grep -iE 'sk_live_|sk_test_[a-zA-Z0-9]{20,}|whsec_[a-zA-Z0-9]{20,}|ghp_|eyJhbGciOi' && echo "BLOCK: real-looking secret in diff" || echo "OK: no common secret prefix"

# Real runtime env files must not retain example placeholders
grep -rE 'CHANGE_ME|PLACEHOLDER|dev_internal_key' apps/api/.env services/ai-engine/.env 2>/dev/null && echo "BLOCK: placeholder remains in real .env" || echo "OK: real .env has no placeholders"
```

Pattern checks are only a supplement. A secret can lack a recognizable prefix;
manual review and the repository Release Security secret scan remain required.

## 4. The `.env` vs `.env.example` rule

| File | Purpose | Committed? | Contains real secrets? |
|---|---|---|---|
| `.env.example` | Template showing required variables | **Yes** | **Never** — blank/fake placeholders only |
| `.env` | Real runtime configuration | **Never** | **Yes** — real passwords, keys, tokens |

The `.gitignore` enforces this pattern. If a real `.env` is accidentally staged,
remove it from the index before pushing while leaving the local runtime file on
disk.

## 5. What to do if a secret or verification credential was committed

If a real secret was pushed to any branch, assume it is exposed and invoke the
incident/rotation procedure immediately. Do not rely on deleting the latest
commit because Git history, caches, forks, CI logs, or notifications may retain
it.

Actions must be performed by the authorized owner for that secret family and
recorded using sanitized evidence. At minimum:

1. contain use of the exposed credential/material;
2. issue/activate replacement secret material through the approved secret
   management path;
3. update affected runtime services under the controlled change procedure;
4. revoke the exposed version where provider/service capabilities allow;
5. review sanitized logs for misuse during the exposure window;
6. verify the replacement without writing the new value into evidence;
7. record incident and reviewer sign-off.

Special authentication notes:

- `MFA_ENCRYPTION_KEY` rotation affects persisted MFA seed decryptability and
  requires the controlled key-version/migration procedure in the Sprint 48
  operational runbook. Do not blindly replace it.
- `AUTH_VERIFICATION_PEPPER` rotation intentionally makes outstanding phone
  verification challenges unverifiable; follow the documented invalidate and
  reissue policy.
- exposure of a raw active email/phone verification challenge should cause the
  challenge to be invalidated/reissued; never copy it into an issue as proof.

History rewriting may reduce accidental exposure footprint but does not replace
credential rotation/revocation.

## 6. Generated Python metadata

`pip install -e .` in `services/ai-engine/` can generate local package metadata
such as `*.egg-info/`. These files are environment-generated and should not be
committed. Keep generated build/runtime artifacts out of pull requests even
when they contain no secret material.
